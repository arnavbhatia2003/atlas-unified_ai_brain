Atlas connects source records, candidate asset identities, document evidence and operational observations in one browsable system. Its strongest contribution is the integrated workflow. Its weakest foundation is deciding what the same asset means across sources and over time.

A defensible project statement

“An assistive prototype for reconciling a bounded set of equipment records and presenting source-backed context, with explicit uncertainty and human review.” This claim becomes stronger after the publication, identity and evaluation defects below are corrected. A working UI and passing integration tests currently support execution, not industrial correctness.

02 / Define the decision first

The problem is larger than duplicate detection

Industrial sources disagree at several different levels. A serial-numbered pump, its operating position, its motor, its pressure signal, a maintenance event and a drawing symbol can all mention P-101. Some pairs represent the same physical item. Most are relationships between different things.

Identity and semantics

Determine entity kind and equipment boundary; qualify source keys; distinguish equipment from position, component, type and measurement. Then decide same physical instance, different instance, related entity, or insufficient evidence.

Lifecycle and changing assertions

Track replacement, movement, key reuse, schema changes and late corrections. Identity continuity and time-valid installation are separate questions. A current crosswalk cannot assign every historical reading correctly.

Context and operational evidence

Extract incidents, completed work, obligations and document references without turning mentions into identity or correlation into causation. Keep competing source assertions visible.

Governance and delivery

Publish only approved results; preserve source versions; replay and reverse merges; restrict access; report degraded coverage; measure error, review effort, latency and cost.

03 / Implemented, not aspirational

How the current code actually works

Open interactive Archify architecture ↗Architecture specificationOffline counterexample script

Architecture shows module paths, not independently deployed services. Postgres stores raw and derived objects in the same database. Archify validation and browser evidence are artifact checks; they do not certify the backend design. Model calls require an external provider.

What is worth keeping

One database is a sensible prototype choice. Raw records are stored before physical projection; the resolver has a replaceable scoring interface and a useful identifier-conflict guard; workflow evidence collection is separated from reasoning; no-failure and no-rule paths can avoid model calls; document parsing is lazy and off the event loop; tests can inject reasoners and stores. Preserve these seams while correcting publication and semantics.

11 / Make evidence repeatable

A test strategy that can support a defense

What has been verified

The previous integration run passed 43 backend tests with the local database; clean frontend install, build and lint completed (four lint warnings); 11 routes were checked on desktop/mobile without observed JavaScript crashes. GitHub CI passed for the audited revision.

Verified CI run ↗

For this assessment, nine deterministic offline counterexamples reproduced defects. They exercise real resolver, schema, anomaly, calibration and embedding code; only external dependencies and controlled pattern fixtures are mocked.

What those checks cannot establish

Passing execution paths do not measure industrial entity accuracy, prompt robustness, load capacity, security, PDF coverage or provider uptime. The existing eval suite uses a few demo expectations, omits some unresolved outputs from its averages, and measures determinism separately from truth.

Counterexamples prove a failure is possible under the supplied input; they do not measure its frequency. The probe script asserts existing wrong behavior, so a successful fix should make the relevant assertion fail until the script is revised into a regression test.

Proposed evaluation protocol

  1. Write the identity policy. One equipment family, one site, physical assembly vs component, allowed key scope, replacement/movement continuity, relation labels and unknown outcomes.
  2. Create two frozen populations. A representative labeled sample and a separate challenge set: reused tags, identical models, OCR, missing IDs, cross-site collisions, replaced motors, point recreation, wrong source keys, late events and no counterpart. Record sampling and counts.
  3. Adjudicate independently. Preserve literal source evidence and reviewer decisions. Use a second reviewer for disputed cases and a defined audit subset. “Insufficient evidence” is a valid label. An LLM may assist annotation but must not judge its own answer as ground truth.
  4. Split by entity and time. Keep all aliases/duplicate passages of an asset together; add site/schema-held-out tests only when data exists. No future corrected crosswalk in prospective model input. Lock thresholds on development/calibration data.
  5. Compare cheap baselines first. Qualified exact keys; conservative lexical rules; probabilistic or supervised comparison. Add embeddings, graph context and selective LLM calls one at a time against the same input, candidate set and label budget.
  6. Publish failures and denominators. Include abstentions, invalid JSON, provider errors, missing candidates and dropped documents. Do not award safety points for returning nothing.

A small dataset supports a small claim

A first target could be 1,000 records across two or three sources, with a few hundred adjudicated decisions and at least 100 challenge cases. These are proposed experiment budgets, not an available dataset or an assurance guarantee. A single site cannot establish cross-site transfer. Finish a coherent slice before expanding the platform

This is a proposed 24-week plan for one engineer, not a claim about effort already spent or a guaranteed estimate. A defensible six-month project shows a working vertical slice, measured limitations, reproducible failures and justified tradeoffs. It does not need to replicate enterprise suites.

Keep the scope small

One equipment family, one facility, two or three source contracts, JSON exports and selected PDF documents, approved identity crosswalks, typed installation relationships and evidence search. RCA remains hypothesis support. Compliance remains obligation-evidence coverage.

Defer until evidence demands it

Universal schema inference, every industrial standard, all sector ontologies, streaming telemetry, autonomous writeback, a graph database migration, Airbyte/S3/Redshift rollout, global multi-tenant SaaS and a new foundational matcher. Existing Postgres can support the first defensible registry.

Limits of this assessment

This is a broad code-grounded engineering assessment, not proof that every defect has been found. No penetration test, industrial corpus experiment, load test, hosted-model answer evaluation, full Docling/OCR quality evaluation, paid standards review, backup restoration or vendor deployment benchmark was run for it. Access controls supplied outside this codebase were not inspected. Research source ledgers were not independently re-audited paper by paper.

The conclusion is actionable: narrow the meaning of identity; stop unapproved claims entering authoritative views; preserve versions and time; fix the reproduced defects; then demonstrate quality, coverage and cost on a frozen labeled slice. That is a credible software engineering project even when the wider industrial problem has no universal solution.
